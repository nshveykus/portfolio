## Описание проекта

Этот проект создан для отработки навыков написания SQL-запросов на примере реальной бизнес-логики интернет-магазина. 

В рамках проекта я:
- Спроектировал схему базы данных (9 таблиц) с учетом связей, внешних ключей и нормализации.
- Наполнил MYSQL базу мок-данными (пользователи, товары, заказы, отзывы).
- Отработал 15+ типовых задач тестировщика и аналитика: от поиска дубликатов до оконных функций и CTE.

## Структура базы данных
В MySQL схемы (Schema) и базы данных (Database) — это одно и то же. Поэтому я создал отдельную базу `toystore`  
База `toystore` состоит из следующих таблиц:

- **`users`** — пользователи (email, хеш пароля, ФИО, дата регистрации, флаг бана).
- **`categories`** — категории товаров (поддерживается древовидная структура `parent_id`).
- **`products`** — товары (цена, остаток на складе, привязка к категории).
- **`orders`** — заказы (пользователь, статус, способ оплаты, итоговая сумма).
- **`order_items`** — состав заказа (товары, количество, цена на момент покупки).
- **`payment_methods`** и **`order_statuses`** — справочники.
- **`reviews`** — отзывы пользователей на товары.
- **`carts`** — корзина (поддерживаются авторизованные и гостевые сессии).

## 🧠 Примеры выполненных задач (Чек-лист)

| № | Запрос | Навык |
| :--- | :--- | :--- |
| 1 | Поиск дубликатов по email | `GROUP BY`, `HAVING` |
| 2 | Поиск заказов-сирот (без пользователей) | `LEFT JOIN`, проверка на `NULL` |
| 3 | Топ-5 популярных товаров | `JOIN`, `SUM`, `ORDER BY`, `LIMIT` |
| 4 | Процент отменённых заказов | `SUM(CASE WHEN...)` |
| 5 | Пагинация (2-я страница заказов) | `LIMIT`, `OFFSET` |
| 6 | Номер заказа по счету у пользователя | `ROW_NUMBER() OVER(PARTITION BY ...)` |
| 7 | Подсчет «лояльных» клиентов (>1 заказ) | `CTE (WITH ... AS)`, вложенные агрегации |

Полный список запросов можно посмотреть в папке `/queries` (скоро добавлю).

## Каким неочевидным вещам я научился

- **Тип TIMESTAMP** хранит время в UTC и автоматически конвертируется под часовой пояс клиента. При фильтрации по датам всегда нужно учитывать время (использовать `>=` и `<` вместо `BETWEEN`, чтобы не потерять заказы за последний день).
- **Разница между INNER JOIN и LEFT JOIN** критична для тестирования: первый скрывает отсутствующие данные, второй — находит «битые» связи.
- **Оконные функции** (ROW_NUMBER, RANK) решают задачи ранжирования в одну строку, которые раньше требовали сложных подзапросов.
- **CTE (Common Table Expressions)** делают сложные запросы читаемыми, разбивая их на логические шаги (как я сделал с подсчетом процента лояльных пользователей).
